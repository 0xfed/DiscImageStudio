# CD 音声トラックの形式、バイト順序、二重像の調査

## ディスク内ファイルとデータディスク

CD プロジェクトのデザインまたはエクスポートページでディスク内ファイルのフォルダーを選ぶと、自動的に ISO9660/Joliet データディスクへ切り替わり、出力拡張子は `.iso` になります。フォルダーパスを消すと WAV 音声トラックに戻ります。ファイル配置は内周または外周で、既定は内周、設定はプロジェクトに保存します。ファイルシステムのメタデータはディスク先頭に残り、外周モードではファイル内容を末尾へ置きます。描画は元のディスク全体の座標を保持し、残り領域へ圧縮しません。

```powershell
DiscImageStudio.exe cd-generate --input picture.png --output cd-image.iso `
  --data-dir "D:\随盘文件" --volume-label CD_IMAGE --file-position outer
```

ISO の長さは `sectorCount × 2048`（sectorCount はセクター数）で、CD-ROM Mode 1 データディスクとして書き込みます。アプリ内のオンザフライ書き込みも同じ ISO データストリームを使います。外部書き込みソフトではイメージ書き込み機能を選んでください。音声インターリーブと CUE は音声トラックモードだけに適用します。データディスクの描画領域では CD-ROM スクランブルと位置マッピングを別途補償し、ディスク内ファイルの内容は元のまま保持します。

CD データディスクのオンザフライ書き込みは音声トラックと DAO セッションおよび lead-out 境界検査を共有し、ATIP 校正したセクター数と完全なファイル配置を保持します。ISO ペイロードを Mode 1 生セクターにエンコードし、データトラック識別子を設定します。Ritek 医療用アクアブルーディスクのプリセットでも 359,845 データセクターを書き、TAO インターフェースの小さい使用可能容量に合わせてパターンやファイルを短縮しません。DAO は音声モードと同じ最大 3 セクターの制限付き overburn 検査を行い、超過時は書き込み前にエラーを報告します。

データトラックは IMAPI のリトルエンディアン主チャネル規約を使用します。標準 Mode 1 セクターに EDC、P/Q 誤り訂正符号、スクランブルを加え、同期ヘッダー `00 FF…FF 00` のバイト順序は保持します。CD-ROM 物理符号化の隣接バイト交換と、リトルエンディアン変換の交換は相殺されます。これは cdrdao の [RAW エンコードと装置バイト順序変換](https://github.com/cdrdao/cdrdao/blob/master/dao/dao.cc)とも一致します。この転送規約でファイルの内外周 ISO 配置や描画の物理座標マッピングは変わりません。

デザイン投影、階調の小プレビュー、有効な `.iso.json` 配置情報付き生成物の読み戻しは、ファイルシステムを含むファイル領域を黄色で示します。同名メタデータはジオメトリ、階調、ファイル配置を記録するため、ISO を移動するときは一緒に移動してください。プレビューは描画ペイロードのマッピングであり、実ディスクの効果は書き込みで確認する必要があります。

## 推奨する使い方

新しい生成ジョブは既定で `cd-track.wav` と `cd-track.cue` を出力します。WAV は非圧縮 PCM、44.1 kHz、16 ビット、ステレオで、データ部分はリトルエンディアンです。両ファイルを同じディレクトリに置き、移動や改名時は CUE 内のファイル名も更新してください。CUE は任意で、エクスポートで「CUE ファイルもエクスポート」のチェックを外すか、コマンドラインで `--cue false` を渡すと WAV だけを書きます。

| 書き込み経路 | 使い方 |
| --- | --- |
| cdrecord | `cdrecord dev=DEVICE speed=SPEED -audio "cd-track.wav"`（DEVICE は装置、SPEED は速度）、`-swab` は追加しない |
| ImgBurn | 「Write image file to disc」で `cd-track.cue` を開く |
| アプリ内ストリーミング書き込み | 同じリトルエンディアン PCM を自動生成し、WAV ヘッダーも完全な一時トラックも作らない |
| 旧 RAW ワークフロー | `.raw` 出力も選択可能。`cdrecord -audio "cd-track.raw"` に `-swab` を付けない |

出力拡張子が実際の形式を決め、`.wav` と `.raw` だけを受け付けます。旧 RAW の改名で WAV には変換できず、再生成が必要です。WAV に付属する CUE は `FILE "cd-track.wav" WAVE` を使い、`BINARY` は使いません。Unicode ファイル名には BOM 付き UTF-8 CUE を使い、空白と中国語に対応します。ImgBurn 作者はこの CUE の Unicode ファイル名対応を確認し、初期 2.5.0.0 の関連問題は 2.5.1.0 で修正済みと説明しています。[ImgBurn 作者の説明](https://forum.imgburn.com/topic/13526-unicode-filename-problem-in-cue-file/)

コマンドライン生成例（ジオメトリには自身の実測設定を使用）：

```powershell
DiscImageStudio.exe cd-generate --input picture.png --output cd-track.wav --interleave true
```

`--cue`（既定 `true`）は WAV と同名の CUE も書くかを制御します。`.raw` 出力では CUE を書きません。

WAV ファイル長は `sectorCount × 2352 + 44` です。音声長、生成進捗、ストリーミング書き込み容量は引き続き `sectorCount × 2352` です。ヘッダーはディスクの音声セクターを使わず、パターンのジオメトリも変えません。

## 階調（ディザリング、sRGB 線形化、階調数、明るさ）

CD の各音声バイトはディスク上で約 6.8 µm の長さに対応します。通常の観察距離では、目は数百から数千バイトを一つの階調に統合します。そのため「各バイトのパターンが白黒だけ」でも「画像が白黒二色だけ」とは限らず、隣接バイトの白黒比率で中間調を再現します。

| パラメーター | 意味 |
| --- | --- |
| ディザリング強度 0–100% | 0% は 128 のハードしきい値（旧動作）。100% はバイトごとに隣接階調を比例選択し、白黒バイトの空間比率で中間調を作る |
| 階調数（CD のみ） | 2 階調は `0x0D` / `0xAA`、4 階調は `0x0D` / `0x10` / `0x63` / `0xAA`（`0x0D` は黒、`0xAA` は白） |
| sRGB 線形化（ガンマ） | sRGB 伝達関数でデコード後にディザリング。出力レベルではなく白黒点密度を変える |
| 明るさ | 階調全体を −64…+64 で移動（0..255 単位） |

コマンドラインオプション（`cd-generate` と `cd-preview-warp` の両方が対応）：

```powershell
DiscImageStudio.exe cd-generate --input picture.png --output cd-track.wav `
  --tone-dither 1 --tone-levels 2 --tone-brightness 0 --tone-gamma false
```

既定値は `--tone-dither 0 --tone-levels 2 --tone-brightness 0 --tone-gamma false` で、旧版とバイト単位で一致します。新規プロジェクトはデザイン右パネルの「階調」で 75% / 2 階調が既定です。`tone` 節のない旧プロジェクトは 0% で読み込み、保存時に `tone` 節を書きます。エクスポートページには出力オプションだけを残し、階調はデザインで設定する旨を出力カードに表示します。

ディザリングの位相は画面座標ではなく**論理バイトインデックス**（`globalByte`）で決まります。遅延インターリーブでファイル内のバイト位置が変わっても、読み戻しは同じ論理インデックスで復元するため、生成、校正投影、読み戻しで同じパターンを見られます。校正パターン（`GeneratePattern`）は固定のハードしきい値を使い、ディザリングしません。

音声トラックの隣の同名 `.json` に `toneDitherStrength`、`toneLevels`、`toneBrightness`、`toneSrgbLinearization` を記録します。プレビューで外部トラックを読み込むと、ジオメトリとインターリーブとともに同期します。

読み戻しプレビューの既定は 1600 px、セクターごとに 16 サンプルで、同じ画素に入るサンプルを**加算して平均化**します。旧版は 900 px、セクターごとに 2 サンプル固定で後の値が上書きし、疎なサンプリングが中間調に白点を残して新聞の網点のように見えました。密度を上げると同じディスクが連続階調に見えます。「デザイン投影」は既定で実測ジオメトリをプロジェクトと同じにし、開いた直後は中立な投影になります。実測半径を入力して初めて両ジオメトリの差を表示します。

## 確認済みの問題

2026-09-12 のユーザーの実ディスク比較では、同じ既存 RAW が cdrecord の `-audio` と `speed` では正常で、`-swab` を加えると二重像を再現しました。これにより、既存 RAW は cdrecord の既定のビッグエンディアン音声入力として解釈すべきと確認できました。

以前はファイル出力とストリーミング書き込みが同一の `GenerateToStream` 出力を共有し、ストリーミング経路でバイト順序を変換しませんでした。しかし入力経路ごとに規約が異なります。

| 入力 | 音声データの要件 |
| --- | --- |
| cdrecord ヘッダーなし `-audio` | 既定はビッグエンディアン |
| cdrecord ヘッダーなし `-audio -swab` | リトルエンディアン。オプションは交換が必要な入力順序を示す |
| cdrecord WAV | ヘッダーを解析し音声バイト順序を自動認識 |
| CUE の `FILE ... BINARY` | リトルエンディアン。既存のビッグエンディアン RAW を BINARY CUE にそのまま指定しない |
| IMAPI `AddTrack(IMAPI_CD_SECTOR_AUDIO, stream)` | 16 ビットのステレオ 44.1 kHz WAV データ部と同じ配置、つまりヘッダーなしリトルエンディアン PCM |

上記の cdrecord の動作と BINARY 定義は [cdrecord 公式マニュアル](https://cdrtools.sourceforge.net/private/man/cdrecord/cdrecord.1.html)、IMAPI の音声サンプル配置は [Microsoft の AUDIO セクター定義](https://learn.microsoft.com/en-us/windows/win32/api/imapi2/ne-imapi2-imapi_cd_sector_type)によります。ImgBurn 作者も `FILE ... WAVE` CUE の書き込み成功例を示しています。[ImgBurn WAVE CUE の例](https://forum.imgburn.com/topic/25173-extract-only-session-two-from-audio-cd/page/2/)

ここで `AudioSectorType = 0` は IMAPI 列挙の AUDIO 値であり、物理 Mode 0 として音声を書き込むことではありません。`IRawCDImageCreator::AddTrack` は現在 AUDIO だけに対応します。[Microsoft AddTrack ドキュメント](https://learn.microsoft.com/en-us/windows/win32/api/imapi2/nf-imapi2-irawcdimagecreator-addtrack)

## 二つの輪郭ができる理由

既存の `CddaInterleaver` は対象バイトに遅延補償を行います。最終出力の各 16 ビットサンプルの 2 バイトを交換すると、異なる遅延位置に属していたバイトが交差して符号化処理に入ります。そのため、通常の音声数値の変化とは解釈できず、画像サンプリング前の一度の交換でも相殺できません。

既存の遅延表で整数ラベルの並べ替え実験を行い、先頭末尾のパディングを除くと、追加のサンプルバイト交換で逆マッピング後の偶数位置は対象バイト `+73` 個、奇数位置は `-73` 個ずれます。これが二重輪郭の機序を説明します。ただしアプリの遅延並べ替えモデルからの導出であり、完全なドライブ CIRC モデルや実ディスク測定ではありません。

修正ではサンプリングと遅延表を保持し、補償後の 2352 バイトセクターの出力境界でバイト順序を選びます。旧 RAW はビッグエンディアン、WAV と IMAPI はリトルエンディアンです。WAV ヘッダーで外部ツールが形式とバイト順序を識別でき、ストリーミングインターフェースには引き続き規約どおりデータ部分だけを渡します。

## 読み戻しでは遅延インターリーブを戻す必要がある

遅延補償は論理バイト i をファイルインデックス `i + offset(i % 24)` に移します。インターリーブ表は 28×D（D=4）フレームの遅延線を、フレームごとに 24 バイトとして保持するため、オフセットは 72～2592（フレーム遅延とフレーム内列回転の和）です。ファイル順に螺旋へ置くとパターン全体が回転・せん断されます。同じ画像で 60000 セクター、900 px の比較では描画画素の約 17.5% が元画像と異なり、「わずかな歪み」に見えます。

そのため `cd-preview-track` は既定で逆マッピング（`--deinterleave`、既定 `true`）を行います。論理バイト i にはファイルインデックス `i + CddaInterleaveTable.FileOffsetFor(i % 24)` を使い、2592 バイトの先読み窓が必要です。順方向遅延は `CddaInterleaver` と `CddaInterleaveTable` を共有するため、両側が独立してずれることはありません。

末尾での代償として、ファイル終了時に遅延線が最後の数フレームを保持し、これらの論理バイトは未出力（1318–1332 バイト、1 セクター未満）なので読み戻しで空白にするしかありません。トラック最外周にあり、全体に対する割合はセクター数が増えるほど小さくなります。

`cd-generate` はトラックの隣に `<track>.json`（`format: cd-da-track-v1`、r0/r1/セクター数/線速度/開始角/画像外半径/インターリーブ有無）を書きます。プレビューはトラック切り替え時に読み取り、校正ジオメトリとインターリーブ設定を読み込むため、他のマシンで作ったトラックも正しいモデルで読み戻せます。

## 校正投影：入力画像と二つのジオメトリ

`cd-preview-warp` は読み戻し経路の高速な比較用で、プレビューの「校正プレビュー」が呼ぶコマンドです。入力はトラックではなく元画像、パラメーターは二つのジオメトリです。生成ジオメトリがバイト i の画像内サンプル位置を、実測ジオメトリがディスク上の描画位置を決めます（`--actual-r0`、`--actual-r1`、既定 24.3 / 56.6 mm）。同じなら元画像が投影され、異なれば実測ディスクに従ってずれます。これが半径校正で観察すべき現象です。セクター数、線速度、開始角、画像外半径は両者で共有し、後ろ三つは 1200 mm/s、0°、57.5 mm 固定です。

元画像だけを読みトラック全体を走査しないため、半径やジオメトリ変更時の更新コストはトラック容量（80 分ディスクで約 845 MB）でなく画像サイズに依存します。校正プレビューで設定を試し、読み戻しシミュレーションで最終ディスクを確認する用途に適します。

## 検証と限界

- RAW と WAV：非対称パターンで、インターリーブ有効・無効の両方について、WAV の data 部は旧 RAW を 16 ビットごとに交換したバイト列と厳密に一致し、長さは変わりません。
- ストリーミング出力：Seek/Position を禁止した前進ストリームで生成したリトルエンディアン音声は WAV の data 部とバイト単位で一致し、ヘッダーを含みません。
- WAV プレビュー：RIFF の `fmt ` / `data` を解析し、未知チャンクと奇数長パディングを読み飛ばし、読み取り範囲を制限してバイト順序を正規化します。PCM 以外、44.1 kHz 以外、16 ビット以外、ステレオ以外は拒否します。異なるサンプル間隔でも対応する RAW プレビューと一致します。プレビューはファイルバイトのマッピングであり、完全な物理 CIRC/EFM を模擬せず、実ディスク判定には代わりません。
- 読み戻し整合性：同じ画像からインターリーブ有無のトラックを生成し、有効側を `--deinterleave true`、無効側をファイル順に読み戻すと、遅延線末尾の 1 セクター以内の画素を除き一致します（900 px 非対称画像で差は末尾投影内だけ。フレーム遅延を 24 バイト変える変異テストは 245 箇所の不一致を報告）。
- 校正投影整合性：同じ画像を生成ジオメトリ `(24.5, 56.8)` でトラックにし、`cd-preview-warp` の投影（実測=生成、実測=`24.3/56.6`）を、対応するジオメトリの `cd-preview-track` 読み戻しと画素比較します。しきい値処理後は完全一致（900 px）します。実測半径を縮めると投影の重心半径も減り、二つのジオメトリが取り違えられないことを確認します。
- Windows メモリ実験：既存の `MsftRawCDImageCreator` に非対称音声 300 セクターを渡し、各 2448 バイト RAW 出力セクター全体を走査すると、全音声バイトがそのまま保持されます。生成器は呼び出し側に代わってバイト交換しません。実験は書き込み装置を作らず、ディスクにも書きません。
- 2026-09-12、修正後にユーザーが実ディスクを試し、二重像がなくなったと報告しました。ユーザー提供の実ディスク結果であり、ストリーミング、cdrecord、ImgBurn の各経路の実測詳細は個別に記録していません。

Microsoft の `WriteMedia` ドキュメントは内部のバイト交換実装を説明していません。上記の結論は、メモリ実験を装置転送中の交換の観測と同一視していません。[Microsoft WriteMedia ドキュメント](https://learn.microsoft.com/en-us/windows/win32/api/imapi2/nf-imapi2-idiscformat2rawcd-writemedia)
